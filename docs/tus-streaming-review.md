# TUS 스트리밍 쓰기 검토 (2026-10-26)

목표: 탐색기 복사가 끝나는 시점 = 서버에 올라간 시점(SMB처럼 한 단계)이 되는 두 번째 마운트 방식.
GUI에서 공간별로 "안정형(rclone 쓰기 캐시)" / "즉시 반영형(TUS 스트리밍)"을 고르게 한다.

## 왜 지금 방식(rclone)은 두 단계인가

- 쓰기 캐시 모드에서 rclone은 파일을 로컬 캐시에 받고, 핸들이 해제될 때 업로드한다.
- Windows 닫기는 Cleanup(앱이 기다림) → Close(비동기) 두 단계다. WinFsp 2.1의 FUSE 계층은 `Flush`와 `Release`를
  **둘 다 Close에서** 부른다(`fuse_intf.c`). Cleanup에서 flush하는 `-o FlushOnCleanup`은 2.2 베타부터다.
  rclone의 `RWFileHandle.Flush`는 크기만 갱신하고, 업로드는 `Release`에서 일어난다(cmount `fs.go`, vfs `read_write.go`).
- `--vfs-write-back 0`(동기식)으로 바꿔도 Release에서 기다릴 뿐이라 탐색기는 기다리지 않는다. 오히려 WinFsp 작업 스레드만 묶인다.

## 서버 쪽 사실 (OpenCloud 7.2.4, 실측)

- TUS 1.0.0. `Tus-Extension: creation, creation-with-upload, checksum, expiration`.
  - 없음: `concatenation`(병렬 조각), `creation-defer-length`(크기 나중 지정), `termination`.
  - → **크기를 생성 때 알아야 하고, 한 줄로 순서대로 PATCH** 해야 한다.
- 권장 조각 `max_chunk_size` 10,000,000. 128MB 조각도 받아 줌.
- 512MB 순차 PATCH(PC → Traefik → OpenCloud):

  | 조각 | 속도 | 마지막 PATCH | 읽기 가능 |
  |---|---|---|---|
  | 10 MB | 30.0 MB/s | 4.3 s | 즉시 |
  | 32 MB | 33.1 MB/s | 4.8 s | 즉시 |
  | 128 MB | 34.9 MB/s | 7.0 s | 즉시 |

  단일 PUT(41~50 MB/s)보다 약간 느리다. 마지막 PATCH가 길게 걸리는 건 서버가 전체 체크섬을 계산하기 때문(약 10 s/GB).
  응답이 오면 곧바로 HEAD 200 → "완료 = 서버에 있음"이 보장된다.

## 탐색기 쓰기 패턴

- 복사 전에 대상 크기를 먼저 정한다(로그의 `WriteFileHandle: Truncate`). → TUS `Upload-Length`로 쓸 수 있다.
- 큰 파일은 겹친 비동기 쓰기(여러 조각 동시 발행)라 WinFsp 스레드에서 **약간 순서가 뒤바뀌어** 도착할 수 있다.
- 복사 끝에 시간·속성 설정(SetBasicInfo) → PROPPATCH로 처리.
- 기존 파일 일부만 고치는 프로그램(DB, VHD, 오피스 일부 저장 방식)은 무작위 쓰기 → 스트리밍 불가.

## 설계안: 하이브리드 쓰기 핸들

1. 읽기·목록·이름 변경 등은 지금처럼 rclone VFS.
2. 쓰기용으로 열린 **새 파일 또는 0으로 잘린 파일**이고, 첫 쓰기 전에 크기가 정해지면 → TUS 업로드 생성.
3. 도착한 쓰기를 **재정렬 버퍼**(예: 64~128MB)에 모았다가 연속 구간이 생기면 PATCH. 버퍼가 차면 쓰기를 잠시 막는다
   (= 탐색기 진행 막대가 실제 업로드 속도를 따라감).
4. 버퍼 밖 무작위 쓰기, 크기 미지정, 크기 변경이 오면 → 그 핸들은 **rclone 쓰기 캐시로 넘김**(지금 방식으로 안전하게 후퇴).
5. 마지막 쓰기 뒤 탐색기가 수정 시각을 정하는 호출(`Utimens`, 앱이 기다림)에서 서버 처리 완료까지 기다린 뒤 반환
   → 탐색기는 서버 반영 후 "완료". (`Flush`도 같은 일을 하지만 WinFsp 2.1에선 비동기 Close에서 불려 탐색기가 기다리지 않는다.)
6. 완료 후 VFS 디렉터리 캐시에서 해당 경로를 잊게 해 새 크기·시간이 바로 보이게.

구현 위치: rclone `cmd/cmount/fs.go`(MIT)를 가져와 쓰기 경로만 고친 자체 cgofuse 파일시스템. 공급자 인터페이스에
"스트리밍 업로더"(TUS 지원 시)를 선택 기능으로 추가하고, 지원하지 않는 서버는 GUI에서 선택지를 숨긴다.

## 위험·한계

- **속도는 빨라지지 않는다.** 서버 쓰기·CPU가 병목(약 30~50 MB/s)이라, 탐색기 진행 속도가 그 수준으로 내려온다.
  지금은 로컬 속도로 끝나고 뒤에서 같은 시간이 걸린다. 바뀌는 건 "언제 끝났다고 말하느냐"뿐.
- 큰 파일은 마지막에 체크섬 시간(약 10 s/GB)만큼 100%에서 멈춰 있다. 수십 GB면 WinFsp IRP 타임아웃 확인 필요.
- 병렬 조각이 없어 한 파일은 한 줄 전송. 여러 파일 동시 복사는 파일별로 병렬 가능.
- 업로드 중 네트워크가 끊기면: TUS는 이어 올리기를 지원하므로 재시도 가능하나, 탐색기는 쓰기 오류를 받을 수 있다.
- 재정렬·후퇴 경계, 동시성, 실패 처리까지 검증 범위가 크다. 대략 2~3주 규모.

## 다른 오픈소스 클라우드

| 서버 | 업로드 방식 | 비고 |
|---|---|---|
| OpenCloud / ownCloud oCIS | TUS(순차) | 위와 같음 |
| Nextcloud | WebDAV 청크 v2: 업로드 폴더에 번호 붙은 조각 PUT → `.file` MOVE로 조립 | 조각 5MB~5GB, 서버가 조립(한 번 더 쓰기), 24시간 미사용 시 만료. 조각을 번호로 정렬하므로 병렬 PUT 여지 있음(문서상 명시는 없음) |
| Seafile | 블록 단위 동기화, WebDAV(seafdav) | 공식 가상 드라이브(SeaDrive)는 로컬 캐시 + 백그라운드 업로드 |
| Pydio Cells | S3 호환 게이트웨이(멀티파트) | rclone s3 백엔드로 접근 |

공통점: 어느 쪽도 "쓰는 즉시 서버 파일에 반영되는" 네트워크 드라이브(SMB/NFS 같은 블록 단위 쓰기)를 제공하지 않는다.
공식 데스크톱 앱들도 로컬 캐시 + 백그라운드 업로드(또는 동기화)다. SMB 같은 한 단계 쓰기는 서버 쪽에 SMB/NFS를 직접 여는 방법뿐.
